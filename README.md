# csharp-llm-benchmark

Benchmark runner for evaluating C# solutions generated by local or remote LLMs. It supports two generation modes: the OpenCode coding agent and the pi coding harness — all running against any OpenAI-compatible endpoint such as LM Studio.

The benchmark includes easy, medium and hard C# tasks, hidden MSTest tests,
Docker-based execution, and JSON/Markdown/HTML reports.

## Quick start

1. Copy the example config:

```bash
cp config.example.yaml config.yaml
```

2. Edit `config.yaml` with your LM Studio endpoint, API model and quantization
   label. Display name and publisher are detected from the LM Studio API.

3. Build the .NET evaluation and shared agentic images:

```bash
docker build -f docker/Dockerfile.dotnet8 -t csharp-llm-benchmark-dotnet8 .
docker build -f docker/Dockerfile.agentic -t csharp-llm-benchmark-agentic .
```

4. Run the full benchmark:

```bash
python -m benchmark.cli run --config config.yaml
```

Run only the easy benchmark:

```bash
python -m benchmark.cli run --config config.yaml --difficulty easy
```

Run only the medium benchmark:

```bash
python -m benchmark.cli run --config config.yaml --difficulty medium
```

Run only the hard benchmark:

```bash
python -m benchmark.cli run --config config.yaml --difficulty hard
```

Run a single task:

```bash
python -m benchmark.cli run --config config.yaml --difficulty easy --task-id easy-001
```

Resume a run from a task, reusing prior `result.json` files from an existing
results folder:

```bash
python -m benchmark.cli run --config config.yaml --resume hard-010
```

When `--resume-dir` is omitted, the runner prompts you to choose a folder under
the configured `benchmark.output_dir`. For non-interactive use, pass it
explicitly:

```bash
python -m benchmark.cli run --config config.yaml --resume hard-010 --resume-dir results/2026-05-16_090131_qwen3.5-4b-q6_k_Q6_K
```

The runner pipelines generation and evaluation: after a task is generated, its
Docker build/tests run in the background while the next task is generated. By
default one evaluation runs at a time. To allow multiple Docker evaluations at
once:

```bash
python -m benchmark.cli run --config config.yaml --evaluation-workers 2
```

By default the runner uses **temperature discovery** mode: it first probes a
small fixed sample of 7 tasks across multiple candidate temperatures (`0.2`,
`0.4`, `0.6`, `0.8`) and then runs the full benchmark **only at the winning
temperature**. This saves time compared to running every task at every
temperature while still finding the temperature that scores best for a given
model.

The two-phase flow works as follows:

1. **Discovery** — 7 tasks (covering basic parsing, generics, algorithms,
   Web APIs, SOLID/OOP, advanced concurrency, and composition design) are run
   at each candidate temperature. The temperature with the highest earned points
   wins; ties break in favour of the lowest value.
2. **Full benchmark** — all selected tasks are run at the winning temperature
   only. This score becomes the final result.

The summary reports include a "Discovery Results" section (in `summary.md`)
and a `discovery` key (`summary.json`) showing per-temperature scores from the
probe round alongside the full benchmark results.

To **disable** discovery and revert to the legacy multi-temperature behaviour
(every task at every temperature), set `llm.discovery.enabled: false` in your
YAML or pass `--discovery-enabled false` on the CLI:

```bash
python -m benchmark.cli run --config config.yaml --discovery-enabled false
```

When discovery is enabled and `--task-id` targets a **non-discovery task**,
discovery is skipped automatically so you can test individual tasks directly.
The `--resume` flow detects whether a previous run already completed the
discovery phase and reuses the winning temperature when available.

Reports are written under `results/<timestamp>_<modelLabel>_<quantization>/`.
With discovery enabled, per-task artifacts from the probe round live under
`discovery/tasks/`, and the full-benchmark output sits at the top level:
```
results/<run-dir>/
├── discovery/
│   └── tasks/
│       ├── easy-003/result.json
│       └── ...
├── tasks/                    # full benchmark (winning temperature)
│   ├── easy-001/result.json
│   └── ...
├── summary.json              # includes "discovery" section
└── summary.md                # includes "Discovery Results" table
```

For legacy multi-temperature runs (discovery disabled), per-task artifacts are
grouped under `temperatures/temperature-<value>/tasks/<task-id>/`, and the
top-level `summary.json`/`summary.md` promotes the best temperature as the final
result. When resuming a multi-temperature run, the runner reuses every existing
`result.json` for each task/temperature pair and queues only missing pairs from
the requested resume task onward. Tasks before the resume task must already have
results for all configured temperatures.

The OpenCode generator omits optional sampling parameters unless
they are configured in YAML or passed on the command line. When omitted, the
provider, for example LM Studio, applies its own defaults.

## Agentic generators

### Speed calibration and agent timeouts

By default, the runner uses `benchmark.generation_workers` (or
`--generation-workers`) directly for speed calibration, temperature discovery
and task generation. Set it to at most the concurrent predictions configured
in LM Studio. The runner does not change or automatically read that server setting.

Concurrency search is **optional and disabled by default**. Enable it with
`benchmark.calibration.concurrency_enabled: true`, or for a single run:

```bash
python -m benchmark.cli run --config config.yaml --concurrency-calibration-enabled true
```

When enabled, the runner treats `generation_workers` as the search ceiling
and tests 2, 3, 4, ... up to this ceiling before speed and timeout calibration,
warming up each candidate and measuring `benchmark.calibration.rounds` rounds.
Each round sums the requests' output tokens/s; the mean across rounds determines
the candidate's throughput. The candidate with the highest throughput becomes
the effective `generation_workers` for temperature discovery and task generation.
Ties choose the smaller concurrency. All candidates are tested, even after a
drop, to avoid missing a later peak. A ceiling of 1 keeps sequential execution
and skips the concurrency search.

With either the configured or selected concurrency, the runner warms up the model with that many
simultaneous requests, waits for all of them to finish,
then measures three rounds at the selected concurrency. Warmup measurements are
discarded when choosing the speed. The slowest measured request sets the common
session timeout for both Pi and OpenCode:

```text
timeout = max(min_timeout_seconds,
              ceil(safety_factor * (token_budget / tokens_per_second + overhead_seconds)))
```

The defaults in `benchmark.calibration` are 128 warmup output tokens per request,
512 output tokens per measured request, a 65,536 token session budget, a 2x safety
factor, 120 seconds of overhead, and a 300 second minimum. The token budget is an
estimate across all agent turns, not a token limit enforced on the agent. Slower
models get more time. This remains a deadline for an entire agent session; it
does not detect loops or guarantee that every productive session will finish.
Increase the budget, overhead, or safety factor for longer tasks or contexts.

Speed is **output tokens per second per request under concurrent load**, using
the provider's `usage.completion_tokens` divided by elapsed request time. It
includes request latency, prompt processing and any reasoning tokens counted by
the provider. It is not aggregate server throughput or pure decoding speed.
These short prompts do not reproduce the growing context of an entire agent
session; the configurable overhead and safety factor provide headroom.
CLI overrides are applied before calibration. Disabling the optional concurrency
search keeps speed and timeout calibration enabled at the configured worker count.

The probes are unscored OpenAI-compatible streaming requests to the configured
model and endpoint. The endpoint must support `stream_options.include_usage`.
Concurrency trials, selected workers, tokens and time are saved separately in `calibration.json` and in the
summary, and excluded from task totals and scores. `request_timeout_seconds`
(default 600) guards each probe; if calibration fails, the run stops with a
diagnostic instead of silently using a fixed agent timeout. When running
`--generator all`, both agents share one concurrency selection and speed calibration.

The consolidated HTML and Markdown reports show **Speed Pi (tok/s)** and
**Speed OpenCode (tok/s)** from the same runs that supplied the displayed scores.
Hover over an HTML speed to see its concurrency and session timeout. Older runs
without calibration show `n/a`.

Resuming a calibrated run reuses its saved worker selection, measurements and
timeout without new probes. The model, endpoint, configured worker count (or
search ceiling), sampling parameters and speed calibration settings must match.
The optional search switch applies only to new runs; resume keeps the saved
selection even when that switch is disabled. Calibrations saved
before concurrency selection existed retain their original fixed worker count.
For runs created before calibration existed, resume with
`--calibration-enabled false`. This option also disables calibration for new
runs, which then use the configured fixed `generation_workers`,
`pi.timeout_seconds` and `opencode.timeout_seconds`:

```bash
python -m benchmark.cli run --config config.yaml --calibration-enabled false
```

The default generator is OpenCode. Both OpenCode and pi run inside the shared agentic image:

```bash
docker build -f docker/Dockerfile.agentic -t csharp-llm-benchmark-agentic .
```

Use `--generator all` to run both OpenCode and pi, or select either agent
explicitly with `--generator opencode` or `--generator pi`. The `llm` config
section supplies the shared model and endpoint settings. Both agents require
a pinned version in their corresponding config sections.

### OpenCode generator

Set a pinned OpenCode version in `config.yaml`:

```yaml
benchmark:
  generator: "opencode"

opencode:
  version: "1.18.5"
  prepare_ahead: true
  precreate_container: false
  # Optional, but useful for OpenAI-compatible/custom providers.
  context_limit: 131072
  output_limit: 8192
  compaction:
    auto: true
    prune: true
    reserved: 10000
```

You can also select it from the CLI:

```bash
python -m benchmark.cli run --config config.yaml --generator opencode --opencode-version 1.18.5 --difficulty easy --task-id easy-001
```

OpenCode is installed inside Docker into `opencode.cache_dir`, grouped by
package and pinned version, and is not read from the host machine. The default
cache is `.cache/opencode`, so future runs with the same OpenCode package and
version reuse the existing install. The agent receives only the task public
files, writes the configured `generated_file`, and the normal hidden-test Docker
evaluation still runs separately with networking disabled. If `llm.base_url`
points to `localhost` or `127.0.0.1`, the OpenCode container uses
`host.docker.internal` unless `opencode.container_base_url` is configured.
Before task generation starts, the runner performs the OpenCode install/cache
check once per benchmark run. With `opencode.prepare_ahead: true`, it prepares
the next task workspace, config and home directory while the current OpenCode
session is running, but still starts only one LLM-backed OpenCode session at a
time. Set `opencode.precreate_container: true` to also `docker create` that next
task container ahead of time; the container is only started after the current
session finishes. The per-task `opencode-home/` directory is transient and is
removed after each OpenCode session completes.
When `context_limit` and `output_limit` are set, the generated OpenCode config
passes those model limits to the custom provider so automatic compaction can
track the remaining context window. `opencode.compaction` controls OpenCode's
automatic context compaction behavior.

### Pi generator

To run tasks through the [pi coding harness](https://github.com/earendil-works/pi-coding-agent), set a pinned pi version in `config.yaml`:

```yaml
benchmark:
  generator: "pi"

pi:
  version: "0.82.1"
  timeout_seconds: 900
  verify_build: true
  build_fix_rounds: 3
```

Or select it from the CLI:

```bash
python -m benchmark.cli run --config config.yaml --generator pi --pi-version 0.82.1 --difficulty easy --task-id easy-001
```

Pi is installed inside Docker into `.cache/pi`, grouped by pinned version, and
is not read from the host machine. Future runs with the same pi package and
version reuse the existing install. The agent receives only the task public
files, writes the configured `generated_file` via its built-in tools (`write`,
`edit`), and the normal hidden-test Docker evaluation still runs separately with
networking disabled. Pi uses `.pi/SYSTEM.md` in the workspace for C# solution
rules and a custom provider defined in `models.json` pointing at the same
OpenAI-compatible API configured in `llm.base_url`. If `llm.base_url` points
to `localhost` or `127.0.0.1`, pi translates it to `host.docker.internal`
automatically.

### Agentic generator notes

Pi and OpenCode session output is written directly to each task's
`pi-events.jsonl` / `pi-stderr.log` or
`opencode-events.jsonl` / `opencode-stderr.log` while the agent runs. The runner
reads JSONL events one at a time to extract usage and errors; it does not retain
the full session output in RAM. Partial logs remain available after a timeout
or interruption. OpenCode's `response.md` remains a copy of its event log.
Retries replace the current OpenCode session logs, as before.

Pi logs are compact by default: final messages, tool calls/results, errors and
context compactions are kept; `message_update` and `tool_execution_update`
streaming events are discarded before writing to disk. To retain those updates
for diagnosis, set `pi.full_event_log: true` in YAML. Both settings count token
usage only from final `message_end` events and compaction results, avoiding the
duplicate message snapshots in `turn_end`, `agent_end` and streaming updates.
Historical `result.json` files keep their previously recorded token totals.

Timed-out OpenCode containers are removed by default. For debugging a stuck
agent, set `opencode.keep_timed_out_containers: true`; the timed-out container
name is then recorded in the task `result.json` under `opencode.container_name`,
and the task `opencode-home/` directory is preserved for inspection.

## Feature addition and complete campaigns

The `evolution` suite evaluates changes to a working C# project. Its six scored
pilot tasks total 120 points, with two tasks per difficulty:

| ID | Difficulty | Feature | Points |
| --- | --- | --- | ---: |
| evolution-easy-001 | easy | Non-throwing stack operations | 10 |
| evolution-easy-002 | easy | HTTP catalog filtering and sorting | 10 |
| evolution-medium-001 | medium | Atomic reservation rescheduling | 20 |
| evolution-medium-002 | medium | Ordered notification fallback | 20 |
| evolution-hard-001 | hard | Durable SQLite stock reservations and release | 30 |
| evolution-hard-002 | hard | Outbox retry backoff and dead letters | 30 |

Both Pi and OpenCode receive the complete public project and may create,
modify or remove permitted C# sources. Namespaces are preserved. Project files
and dependencies remain fixed. Hidden tests are absent during generation.
The reservations task evaluates room moves, conflict rollback, validation,
concurrent changes and preservation of the existing HTTP contracts. Its starter
contains a working controller, domain store, DTO and DI registration; the requested
feature is `PUT /reservations/{id}/schedule`.

Evaluation reconstructs the delivered project and runs separate hidden feature
and regression test projects. The score is the weighted feature pass fraction
multiplied by the weighted regression pass fraction. A working but unchanged
starter receives zero. A complete feature with all previous behavior preserved
receives 100. Compilation is a prerequisite with no separate points. JSON and
Markdown summaries show both fractions; `delivery.json`, `delivery/` and
`changes.diff` record the evaluated sources.

List or validate the pilot:

```bash
python -m benchmark.cli list-tasks --suite evolution
python -m benchmark.cli validate --suite evolution
python -m benchmark.cli validate --suite evolution --execute
python -m benchmark.cli list-tasks --suite evolution --role discovery
python -m benchmark.cli validate --suite evolution --role all --execute
```

The executable validation checks that each starter passes every regression and
earns zero feature points, and that the reference passes both groups.
Reference sources are overlaid on the starter project. The opt-in Docker tests
also evaluate deliberately broken features and old contracts, including stock
reservation limits, retry schedules, case-insensitive queries and channel names.
They confirm that these changes reduce the score. The existing greenfield SQLite
reference also runs to verify native dependency loading:

```powershell
$env:BENCHMARK_DOCKER_TESTS = "1"
python -m unittest discover -s tests -p test_evolution_docker.py
```

Run the pilot against both agents, with normal speed/timeout calibration:

```bash
python -m benchmark.cli run --config config.yaml --suite evolution --difficulty all --generator all
```

Run only the stack task against both agents:

```bash
python -m benchmark.cli run --config config.yaml --suite evolution --generator all --task-id evolution-easy-001 --discovery-enabled false
```

Run the medium reservations task against both agents:

```bash
python -m benchmark.cli run --config config.yaml --suite evolution --difficulty medium --generator all --task-id evolution-medium-001 --discovery-enabled false
```

Run both hard tasks:

```bash
python -m benchmark.cli run --config config.yaml --suite evolution --difficulty hard --generator all --discovery-enabled false
```

Evolution uses four independent discovery tasks: ordered-set reordering,
JSON report-format integration, atomic HTTP batch completion and durable SQLite
compare-exchange. They contain 41 hidden tests and never enter the 120-point
scored catalog. Every selected difficulty uses the same four discovery tasks.
Greenfield keeps its historical seven-task discovery/reuse policy.
With multiple candidate temperatures and discovery enabled, each `(suite, generator)`
selects its own winner; ties choose the lowest temperature regardless of list order.
Discovery cost and tokens are stored separately in `discovery.json` and the summaries.

For a fixed-temperature run, use one `llm.temperatures` entry. Disabling discovery
with multiple temperatures retains the legacy best-temperature sweep; this is a
diagnostic protocol and cannot produce an official combined ranking.

Earlier runs with two tasks had 30 available points. Compare scores using the
same task catalog and weights; those runs and single-task diagnostics do not
represent the current full 120-point catalog. They remain available as historical runs.

Use `benchmark.suite: "all"` or `--suite all` to run both greenfield and evolution
in one invocation. Together with `generator: "all"`, this executes greenfield
with OpenCode and Pi, then evolution with OpenCode and Pi. Model metadata and
speed calibration are obtained once and shared across all four evaluations.
Each evaluation keeps its own task selection, output directory and summary.

```bash
python -m benchmark.cli run --config config.yaml --suite all --generator all
```

Use `difficulty: "all"`, omit `task_id`, and keep speed calibration enabled for
the complete ranking. The example config selects both suites and both agents.
Existing configs still default to `greenfield` and the OpenCode generator.
A campaign continues the other pairs if one fails and returns a nonzero exit code.

Runs involving evolution now use a campaign directory:

```text
results/<timestamp>_campaign-<id>/
  campaign.json
  calibration.json
  greenfield/opencode/{discovery/, tasks/, summary.json, summary.md}
  greenfield/pi/{discovery/, tasks/, summary.json, summary.md}
  evolution/opencode/{discovery/, tasks/, summary.json, summary.md}
  evolution/pi/{discovery/, tasks/, summary.json, summary.md}
```

The manifest records the exact configuration, generator profiles, task weights,
versions and fingerprints of public/hidden files. It excludes credentials.
Resume all missing work with the same YAML and original suite/generator selection:

```bash
python -m benchmark.cli run --config config.yaml --suite all --generator all --resume-campaign results/<campaign-directory>
```

Completed pairs are reused, partial discovery continues from saved results,
completed discovery keeps its selected temperature, and only missing scored tasks
run again. Configuration or contract changes require a new campaign. Do not change
model, temperatures, sampling, concurrency, timeout settings or agent versions
when resuming. Legacy flat result folders still support `--resume TASK_ID --resume-dir ...`.

Generate the consolidated HTML/Markdown with:

```bash
python benchmark/aggregate_benchmark_results.py
```

The main columns are **Construção**, **Features**, and **Combinado**, with PI and
OpenCode subcolumns and per-pair diagnostics. Each suite averages its two agents;
the combined score averages the suites with equal weights, without rounding
intermediate scores. Missing evaluations are `n/a`, never zero. The combined
ranking requires all four complete evaluations from the same campaign, full task
catalogs, speed calibration, and discovery (or one fixed temperature). It chooses
the latest complete campaign per configuration and versions, not historical best
scores. Partial/newer attempts remain listed separately. Filters, chart, highlights
and score/GiB use the selected metric. Old flat runs stay in an individual history
table and cannot supply a missing combined score.

Single-suite historical best-run views remain available with `--suite greenfield`
or `--suite evolution`; their averaging policy is unchanged and may include
partial diagnostics. These are historical views, separate from the campaign ranking.

Both generators put .NET/NuGet state in `/tmp/benchmark-dotnet` inside their
containers. This avoids NuGet's first-build permission failure on WSL Windows
bind mounts without changing the generator home or requiring an image rebuild.
Their containers also mount each public project's standard `bin` and `obj`
directories as tmpfs with execution enabled. The SDK can update file timestamps
and executable permissions there while source changes remain in the host
workspace. These runtime settings also apply to precreated containers and
projects in subdirectories; an image rebuild is not required.

The evaluator's `/workspace` tmpfs enables executable mappings so native package
libraries such as SQLite can load. `/tmp` remains `noexec`, and the evaluator
retains its existing network, user, read-only root and resource limits.

To verify fresh builds, incremental web builds and executable permissions for
both generators on WSL:

```bash
BENCHMARK_DOCKER_TESTS=1 python3 -m unittest discover -s tests -p test_agent_build_docker.py
```

The shared output and both generator cache paths are resolved at CLI startup,
before calibration and the first suite/generator pair. Task roots and artifact
directories are also anchored before Docker preflight, so preparation and
subsequent pairs do not depend on later working-directory lookups.
Caught task exceptions from preparation, generation or evaluation are written to
`tasks/<task-id>/error.log` inside the run folder. The terminal prints the complete
traceback after the final dashboard update so progress rendering cannot erase it.
Matrix-level failures also print their full traceback, including errors before
a run directory exists.

If WSL reports `No module named 'benchmark'` even while the terminal prompt shows
the project directory, check the actual working directory:

```bash
python3 -c 'import os; print(os.getcwd())'
```

A `FileNotFoundError` here means the terminal's directory reference is no longer
valid. The prompt can retain the previous path. Leave that directory and enter
the project again using its absolute path; for this checkout:

```bash
cd /
cd /mnt/c/dev/ext/csharp-llm-benchmark
python3 -m benchmark.cli run --config config.yaml
```

## Aggregate benchmark results

To generate Markdown and filterable HTML ranking tables from all benchmark run
summaries under the results directory:

```bash
python benchmark/aggregate_benchmark_results.py
```

By default, this writes `results/benchmark_results.md` and
`results/benchmark_results.html`. Running the command again recreates those
files and overwrites their previous contents. The default view ranks compatible
campaigns, with separate construction, feature-addition and combined scores.
Model details show temperatures, agent versions, timeout counts, feature/regression
ratios, calibration, tokens and session time. The historical single-suite views
can still be generated using `--suite greenfield` or `--suite evolution`.

Use `--results-dir` to read runs from a different directory, or `--output` to
write the Markdown report to a different file. The HTML file defaults to the
same path with a `.html` extension, or can be set explicitly with
`--html-output`:

```bash
python benchmark/aggregate_benchmark_results.py --results-dir results --output results/benchmark_results_latest.md --html-output results/benchmark_results_latest.html
```

## Useful commands

List tasks:

```bash
python -m benchmark.cli list-tasks
python -m benchmark.cli list-tasks --difficulty easy
python -m benchmark.cli list-tasks --difficulty medium
python -m benchmark.cli list-tasks --difficulty hard
```

Validate task metadata:

```bash
python -m benchmark.cli validate
python -m benchmark.cli validate --difficulty easy
python -m benchmark.cli validate --difficulty medium
python -m benchmark.cli validate --difficulty hard
```

Run with an API key from the environment:

```bash
LLM_API_KEY=lm-studio python -m benchmark.cli run --config config.yaml
```

Throttle the start of OpenCode sessions when needed. This setting controls
session starts, rather than individual API requests within an agent session. Omit this field, set it to `null`, or set it to `0` to disable the
throttle:

```yaml
llm:
  requests_per_minute: 3
```

Set the API model and quantization label in `config.yaml`.
`model` is sent to the API. The LM Studio API's `display_name` is used in result
folder names, logs and aggregate ranking tables, and saved as `modelLabel` in
results. `publisher` is shown as a separate aggregate table column and also
comes from the API. Legacy `llm.modelLabel`, `llm.model_label` and `llm.publisher`
config values are ignored. If `display_name` is unavailable, the API model ID
is used as the display name:

```yaml
llm:
  model: "qwen3.5-4b@q4_k_m"
  quantization: "Q4_K_M"
```

When running against a local LM Studio server, the benchmark queries its
`GET /api/v1/models` endpoint once at startup and records the model size
(shown in the aggregate **Model Size** column), parameter count, display name
and publisher.
Publisher names have their first letter capitalized, with `lmstudio-community`
rendered as `LM Studio Community` and `prism-ml` as `Prism ML`. If the API lookup
or publisher is unavailable, reports show `n/a` for publisher.

For a server on the same machine (including its LAN address), the benchmark
also uses `lms server status --json` and `lms ps --json`, when `lms` is on PATH.
It checks the server host and port and matches the loaded instance identifier
to `llm.model`. The instance's quantization and file size take priority over
catalog metadata; this handles a generic ID such as `google/gemma-4-12b`
running Q6_K while the catalog advertises Q4_K_M.

For catalog entries with multiple `variants`, neither `quantization` nor
`selected_variant` proves which variant is loaded. If the loaded instance
cannot be resolved (for example, a LAN server or missing CLI), a warning
is emitted. Before calibration or generation, the terminal asks for the
loaded model's quantization and file size in GB. This also applies when local
model metadata is unavailable or incomplete; only missing fields are requested.
The YAML quantization is not used as a fallback for local models.

The size accepts a decimal point or comma and uses the reports' convention
(1 GB = 1024^3 bytes). Blank/unknown quantization and nonpositive or nonfinite
sizes are rejected. Answers are requested once and shared by both generators,
then saved in the reports. If input is unavailable, the run stops before
calibration or generation instead of recording uncertain metadata.

Unambiguous metadata is still detected automatically. Cloud providers continue
to use the YAML quantization. Existing reports are not automatically relabeled.
The size backfill below skips ambiguous catalog entries:

```bash
# Backfill model_size_bytes/params_string into older runs (dry-run first):
python scripts/backfill_model_size.py --results-dir results --dry-run
```

Configure benchmark temperatures in `config.yaml` under `llm.temperatures`.
Omit the field to use the default `0.2`, `0.4`, `0.6`, `0.8` sweep. The legacy
single-value `llm.temperature` field is still accepted for one-temperature
runs:

```yaml
llm:
  temperatures:
    - 0.2
    - 0.4
    - 0.6
```

When discovery mode is enabled (the default), the probe phase uses its own
candidate list from `llm.discovery.temperatures` if set, falling back to
`llm.temperatures`. To use a different set of temperatures only for the
discovery round:

```yaml
llm:
  discovery:
    enabled: true
    temperatures:
      - 0.2
      - 0.4
      - 0.6
      - 0.8
```

You can also override the discovery toggle from the CLI with
`--discovery-enabled true|false`.

Optional sampling parameters are sent to OpenCode only when configured in the
`llm` section:

```yaml
llm:
  top_p: 0.95
  min_p: 0.05
  top_k: 50
  repetition_penalty: 1.0
```

The same values can be supplied from the CLI:

```bash
python -m benchmark.cli run --config config.yaml --top-p 0.95 --min-p 0.05 --top-k 50 --repetition-penalty 1.0
```

You can also set a single task in `config.yaml`:

```yaml
benchmark:
  # Optional: "easy", "medium", "hard" or "all".
  difficulty: "all"
  task_id: "easy-001"
```

## Notes

- Each agent receives shared solution rules, the task contract from `prompt.md`,
  and the public project files.
- Hidden tests are copied into an isolated temporary workspace only during
  evaluation.
- The shared solution rules require agents to write the generated file, avoid
  C# namespaces, target the provided project compiled with the .NET 8 SDK, prefer
  conservative broadly supported C#/BCL APIs, and avoid adding extra
  third-party/NuGet packages.

  caching with single-flight loading, dependency planning, async ETL, priority

  persistence, pricing plugins, immutable tries, specification rules and client

  evaluation can continue with container networking disabled.
